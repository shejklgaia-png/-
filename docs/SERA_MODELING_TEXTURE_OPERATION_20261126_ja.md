# モデスタ・テクスタ連携制作運用
2026-11-26 JST / CRATE V17.2時点

## 1. 適用範囲・位置付け
モデスタとテクスタを用いる新規・改修3D制作の標準手順。パーファクの連携制作にも適用するが、既存の正式工程・承認ゲートを迂回しない。既存のAI監修付き段階分業と全3D生産HTML配布規約を補完する。CRATE V17.2は現時点の比較用改善候補であり、ゲーム採用済みモデルではない。CRATE固有の寸法、ポリゴン数、テクスチャ解像度は他のモデルの必須値としない。

## 2. 制作の順序と役割
1. 着手前に台帳、現行GitHub正本、既存モデル、設定画、成功・失敗記録を確認する。技術的な新規実装では公式資料、実物・類似作品、技術者・企業の事例を比較し、採用理由を記録する。
2. AIが設定画・意図・部品の機能・構成を検討し、外形と構造の設計を行う。モデスタで概形を生成し、実画像を確認する。
3. AIが部品の機構、支持、可動軸、厚み、断面、開口、必要なクリアランスを設計し、モデスタで詳細造形する。既存の良好な形状は維持する。概形確定後の輪郭一致率は参考値とする。
4. 実メッシュの接続、可動干渉、平面性、法線、退化面、ポリゴン予算を検査する。AIが実レンダー・3Dビューワーと比較元を確認し、数値に表れない造形の違和感を特定する。
5. テクスタで実メッシュ・原面・UVを基に塗装する。塗装後の実レンダーを確認し、構造と整合しない線や固定具、色飛び、陰影を修正する。モデスタ側の問題は造形に戻る。
6. AIが問題部品、観察方向、原因、具体変更、維持条件を記録し、再構築→同条件で比較→再監修を行う。各工程で実物を確認し、見ていない成果を合格扱いしない。アルゴリズムの自動探索は課題の候補生成であり、AI監修の代替ではない。
7. 完成候補の実ファイルを提示する。ユーザーの外観評価、技術検査、ゲーム採用、実機確認は別々に管理する。明示的なゲーム反映指示がない限り既存ゲームモデルを置き換えない。

## 3. モデスタの造形基準
- シルエット、大きな装甲面、実際の厚み・凹凸・開口、関節、支持、軸受け、荷重を伝える形状をメッシュで表現する。微細なパネルラインやボルトを無条件に別メッシュ化しない。
- 固定側と回転側、支柱・軸・軸受け・フランジ・ヨークなどの役割を分ける。中空部、支持先、クリアランス、可動時の干渉を確認する。既存ピボットと可動域は理由なく変えない。干渉を隠すための免除追加や可動域縮小をしない。
- 履帯の外周、車輪、転輪、ガイド、支持フレームを独立した構造として設計する。車輪が外装に埋まる場合は軸方向の移動だけでなく直径・中心位置・カバー・軸受けを検討する。接地とシルエットを保ち、正面斜め・真横・左右から確認する。
- 斜め装甲や面取りは意図した傾斜と面の連続性を整える。平面であるべき四角面は非平面残差を検査し、三角形分割による不自然な陰影が出ないよう原頂点から修正する。45度はCRATE頭部での採用値であり、全形状への一律強制ではない。
- 切削・ベベル等で生じた重複頂点・退化面・非多様体は原因を修正する。微小修復は対象を限定し、検査を緩めない。実ゲーム向けのポリゴン予算は対象ごとに判断する。

## 4. テクスタの塗装基準
- モデスタの原面・実共有辺・部品境界・構造を理解してから塗装する。UV上の見かけだけで線を決めない。面をまたぐ線は実3D上でつながるように描画し、投影の対象部品・原面を明示する。
- 装甲の縁を包むフレーム、交換用整備口、固定部、接合に沿う締結具、通風口、凹部内の機構、用途のあるマーキングを優先する。適度な余白を残す。線やボルトの数を品質指標にしない。
- 一律の平面横断線、軸・爪・アンテナの装飾リング、面を埋めるだけの帯、意味の弱い分割線は不要。メッシュ境界としてゲームが描く線をテクスチャへ重複して焼き込まない。
- 面全体の光源方向による明暗・ハイライトはゲーム内ライティングへ委ねる。凹部・隙間の暗がりと材質固有の色を描く。Albedoとゲーム陰影・枠線を独立させる。
- UVの退化、境界の色飛び、テクスチャとGLB内蔵画像の整合性、ラスタ描画衝突を検査する。原面とUVの対応を保ち、隣接面補正は未使用余白に限る。
- 軽微なUV描画衝突は数値だけを理由に作り直さない。スクリーンショット・実モデルの監修で見える色飛びや不要線がなく、材質・描画内容と位置を確認できた場合は記録して許容できる。未調査の重複、可視異常、重大なUV破綻や退化面の免除ではない。CRATE V17.2のNeckYawOutput同一スチール材質の2サンプルはユーザー許容済み。

## 5. 納品・検証
- 制作の中間・最終成果を実モデル内蔵のHTMLで提示する。回転、移動、拡縮、視点リセット、関節操作（該当時）、完成モデル、メッシュ単体／UVグリッド、テクスチャ単体の確認を基本とする。
- 現行ゲーム正本から対象シーン・モデルの描画設定を取得し、ゲーム陰影・ゲーム枠線を独立してON/OFF可能にする。既定ON。テクスチャ表示も独立させる。可視メッシュID境界と深度に基づく枠線を優先し、三角形ワイヤーをゲーム枠線として扱わない。CRATE現行値は外4/内0/境界1px、角線なし、BASE黒、単体プレビュー#17212F。変更時は最新正本を優先する。
- 正面・背面・左右・斜め・上下の実レンダー、比較元、GLB、BLEND、Albedo、設計、検査報告を保存する。画像、UV、メッシュ、ビューワーが同じ制作版のものか識別子・ハッシュで確認する。
- HTMLの構文検査、実ブラウザ操作、Godot読み込み、Android実機確認は別の検査。近似描画をGodot完全一致と称さない。WebGL非対応時の実画像フォールバックは3D操作の代替合格ではない。
- 離散姿勢のBVH交差数は貫通深さ・連続衝突の証明ではない。接続グラフの近接経路は荷重支持の証明ではない。数値は診断として利用し、外観承認は実画像とユーザー判断で行う。

## 6. 開発運用
- GitHubと開発台帳を正本として差分、コミット、PR、マージ、制作run、成果物ID、実監修した画像、検査結果、未確認事項を記録する。
- 失敗時は実ログ・失敗成果物を取得し、発生事象、原因、対処、注意、再発予防を記録して対象だけ再構築する。完成していない成果物を完成扱いしない。
- 既存の専用制作実行を利用する。ゲーム本体のCI確認・修正・適用・テストは禁止。実装作業中に画像生成しない。自動マージ規則と明示的な例外指示は台帳の開発運用に従う。
- 本文は制作運用の規約であり、独立AIエージェント、自動工程ゲート、全旧ビューワー対応を実装したという意味ではない。

## 8. VEXER V10後の造形優先改善（2026-11-26）
- 新規の複雑造形は主要形状の異なる3つ以上の実3D粗案を比較して選定。既存の良好な造形の局所修正は単案可。色や小物の違いだけで別案としない。
- 原画・無彩色・通常材質・小サイズ表示を共通条件で比較し、輪郭、プロポーション、量感、面の連続性を先に審査。採用されない段階で副形状・テクスタへ進まない。独立AIがなければ同一AI監修と記録。
- モデスタのsurface_authoring.finishで曲面/平面/稜線の法線処理を分離。planar_regionsで意図的な主面を診断。clay_reviewで同一ジオメトリの無彩色レンダーを追加。造形欠陥を法線で隠さない。正式納品と承認ゲートは維持。
- VEXER V1〜V10は比較/失敗資料、現時点で完成承認なし。候補を自動採用しない。
