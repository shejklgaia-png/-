# SERA v270 — 横フリックの蹴り優先と実機判定ログ

## 再確認した問題
v269までは、3段コンボ中の蹴り候補であっても、`_combo_kick_side_for_flick` が**セラの前方90°**を返す場合、画面左右へのフリックでも蹴り扱いにできませんでした。

カメラの位置やロック方向によりセラが画面右・左を向くと、画面右・左フリックはセラの前方・後方・横方向を行き来します。v269はセラの後方と画面左右の重複だけを救済したため、**セラ前方で画面左右のフリック**が依然としてバッシュまたは通常STEPになる入力競合が残っていました。

添付されたv268の動画では3段目からBashへ切り替わる箇所と通常STEPへ切り替わる箇所の両方が見られ、蹴り予約表示は確認できませんでした。v269の新規動作は実機動画で未確認なので、以下を**新たな切り分け可能な修正**としています。

## 操作修正
- 3段目の振り抜き中または完全終了後0.65秒以内に入力開始したフリックについて、**セラの正面を基準とする左右各90°セクター**の蹴りを従来どおり優先します。
- それ以外でも、**画面左右（上を基準とした左右各90°）**のフリックは蹴りとして認識します。v269と異なり、セラの前方・後方のどちらに入力された場合も有効です。
- 左右蹴りと前方バッシュの判定が重なるケースでは、**画面左右へのフリックを蹴り優先**とします。セラ前方のうち画面左右と重ならない方向は、これまでどおりバッシュを受け付けます。これは操作の競合解消のための明示的な優先順位変更です。
- 蹴りを受け付けるのはコンボ派生受付期間だけです。それ以外のRUN・BOOSTと画面360°STEPは変更しません。画面操作の方向ベクトル、移動距離2〜4m・速度・EN、衝突・カメラ、元の`Kick_l`/`Kick_r`モーションは維持します。
- 3段目のモーションは最後まで再生してから予約した蹴りを始めます。通常STEPの受付条件、前方Bashの残りの受付条件は維持します。

## 画面上で原因を特定するための表示
同じ挙動がまだ残る場合に、タッチ受付の各段階の失敗を画面録画だけで判別できるよう、既存のトレーニング／戦闘デバッグ欄に結果を2秒間表示します。新しいUI画面は追加しません。

| 表示例 | 意味 |
| --- | --- |
| `KICK: QUEUED L/R` | 3段目中の蹴り入力を予約しました |
| `KICK: START L/R` | 蹴りの移動処理を開始しました |
| `KICK: WINDOW CLOSED` | フリック開始時にコンボ受付期間がありません |
| `KICK: HOLD >0.42s / BOOST` | フリック時間超過またはBOOST入力で候補を失いました |
| `KICK: TOO SHORT / SLOW` | 移動距離または速度が蹴りの条件を満たしていません |
| `KICK: ANGLE` | フリック方向が蹴り受付外です |
| `KICK: CLIP MISSING` | 蹴りアニメーションの実行時ロードに失敗しています |
| `KICK: STATE BLOCKED`、`KICK: EN / ACTION BLOCKED` | 状態異常やENなどで蹴りの開始が拒否されました |

なお、`KICK: WINDOW CLOSED` は**3段目完走後の約1.6秒以内の画面横フリック**にのみ表示し、通常移動中に常時出続けないよう制限しています。表示の期限が過ぎると従来のSTEP実績表示へ戻ります。

## テストと制約
- `tools/v270_kick_input_priority_diagnostic_self_check.py` は、セラの向き全360°を0.5°刻みで確認し、画面左右入力が常に蹴りへ分類されること、セラ基準の蹴りも維持されること、通常STEP・Bashの優先順位、ゲーム内デバッグ表示の接続を静的／数値検証します。
- 旧v269テストは「セラ前方と画面左右が重なる場合の蹴り優先」という新仕様に合わせて更新し、従来のセラ後方・横方向の検査は継続します。
- Android上でv270を実行した実機テストはまだ実施していません。プログラムの分岐を検査していても実機での動作を保証するものではありません。
