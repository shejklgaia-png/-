# SERA モーション実装・再発防止規約

**対象**：新しいBlockbenchアニメーションの追加、既存アニメーション名の変更、リグ／モーション読込・実行処理の変更、鳥脚など骨格別アニメーションの追加。SERAの全開発で継続適用します。

## v264～v273の事例から判明した問題
1. **モデルのJSONにキーが存在することは、実行時に再生できることの証明ではない**。左右Kickのキーは存在したがAndroidで `CLIP MISSING` と判定された。
2. 起動時に `ALREADY READY` と判定されても、**発動時の名前検索・再生開始処理は別の実行経路**である。蹴りにだけ導入した型付き配列と条件演算子を用いた候補名検索は、既存の固定名再生と異なりGodot実行時に失敗し得た。
3. `has_side_kick()` が欠落を補修する前に `start_side_kick()` が再生名を取得する順序の問題もあった。**復旧可能性の判定→復旧→名前取得→開始→結果検証**の順番を守る。
4. Pythonの静的検査・JSON整合性テストが全て成功してもGodot実行時の不具合を検出できなかった。モーション機能は**Godotでの実行検査が必須**。

## 変更時の必須ルール
- **正規化した固定のモーション名を使う**。例：`Kick_l`／`Kick_r`。`animations`辞書のキーとBlockbench/生成JSONの名前を一致させる。必要な互換名検索は例外的に、型・左右の境界を明示して実装する。
- **Godot上で使用する関数をそのまま実行テスト**する。`has_*`の成功だけでなく、`start_*`を呼び、`current_clip`とキーフレーム入りトラック、必要に応じて経過時間・最終姿勢を検査する。候補名検索を新設した場合は、左右・前後・正常／不在入力を検証する。
- **すべての正本アニメーション**はCIの`tools/sera_animation_runtime_smoke.gd`で実リグをロードし、全クリップを実行時に選択・サンプルする。新規クリップは`assets/sera_source.json`を正本として同テストに自動的に含まれる。既存の`tools/v273_kick_lookup_runtime_check.gd`も左右Kickの実際の公開API発動を保護する。
- **生成ファイルの一致**を確認し、`tools/rebuild_model_data.py`など正規の生成スクリプトを使用する。元Blockbenchの関節Pivot／キーフレームを変える必要がなければ触れない。新しい埋込ファイルやフォールバックを安易に増やさない。
- **不具合報告時は最初に実機のHUD・Godotエラーログを確認**し、入力受付／名前検索／ロード／再生開始／描画を区別して原因を特定する。モーションがあることを理由に入力方向を変更するなど、根拠のない修正をしない。
- **診断ログは現在の状態を検査する**。キャッシュされた`ALREADY READY`と`CLIP MISSING`のような矛盾を残さない。失敗箇所を表す短いエラーコード、必要ならクリップ名・骨UUID対応数を表示する。
- **GitHub PR時にGodot実行CIが成功すること**を必須とする。静的検査だけではマージしてはならない。CIが取得するGodotエンジンは`project.godot`のGodot 4.7系と互換な既存の4.7.2を維持し、Android実機での最終確認は別に記録する。

## 最短チェックフロー
1. Blockbench `→` 既存の正本統合 `→` 生成データ一致検証
2. Godotの実リグ起動 `→` 辞書内の正規名検索 `→` キーフレームと実骨格UUID一致
3. 公開APIによる再生開始 `→` `current_clip`照合 `→` 途中・終了フレームの姿勢検査（必要時）
4. 操作で発動するモーションは、コントローラー受付 `→` 戦闘状態 `→` 再生要求 `→` 再生成功の経路も検査
5. 既存アニメーション・モデル／装備・通常STEP／バッシュ・格闘・カメラへの回帰テストを通した後、PRをマージ

**適用境界**：Linux headlessのGodot CIはGDScriptのロード・アニメーション検索・再生開始・骨格計算を検査します。Android特有のタッチ入力感触、描画、音、FPSは自動検証の対象外であり、実機での確認結果を別途残します。
